## 2026-08-12 — `run_gpu_pipeline.sh` bug found live on the real GPU box, fixed same session

- **`run_gpu_pipeline.sh`: `set -o pipefail` added; the script's own sanity check silently reported success after actually failing.** On the first real run (RTX A4000, remote GPU box), `python3 -m pytest ...` failed with `No module named pytest` (pytest was never listed as a dependency anywhere — see below), but because the command was piped into `tee` for logging, `set -e` alone couldn't see the failure (a pipeline's exit status is its *last* command's, i.e. `tee`'s, which is essentially always 0) — the script printed "✓ Test suite passed/skipped cleanly" and moved on. The *next* pytest call happened to not be piped, genuinely failed, and correctly killed the job via `set -e` — which is the only reason this was noticed at all rather than silently sailing through every subsequent `| tee` in the script the same way. Fixed: added `set -o pipefail` immediately after `set -e`, so any command's failure anywhere in a pipe now actually stops the script.
- **Added a preflight dependency check** (`pytest`, `wfdb`, `neurokit2`, `torch`, `numpy`, `sklearn`, `scipy`) at the top of the script, so a missing package fails immediately with a clear message instead of surfacing confusingly mid-log (or, per the bug above, not surfacing at all).
- **`pytest` added to the install instructions** in `PHASE5_SCOPE_PLAN.md` (both the Quick Start and the detailed Section 0) — same class of gap as the `neurokit2` miss (Phase 5 scoping session): a real dependency the pipeline needs that was never listed anywhere.
- **Does not change any reported number** — this is a fix to the orchestration script's own error-handling, not to any training/eval logic.

- **`src/e3c_compliance.py` / `tests/test_e3c_compliance.py`: fixed a test-isolation bug found live on the real GPU box.** `check_criterion_1`/`check_criterion_3` hardcoded the data path (`data/processed_rr_history`) instead of taking it as a parameter. On a machine that had already run the data pipeline (the GPU box), the tests' `NONEXISTENT_DIR` argument (meant to simulate "no real evidence available") did nothing to the hardcoded path — the functions correctly found the real `ids_train.npy`/`ids_test.npy`/`y_test.npy` that genuinely existed there and returned PASS, which is actually correct behavior; the test's assumption that this data wouldn't exist was wrong, not the underlying logic. Fixed: both functions now take an optional `data_dir` parameter (default unchanged, so no behavior change for existing callers); the two affected tests now pass an explicit, guaranteed-empty `tmp_path`-based directory instead of relying on ambient filesystem state. Added two more tests while fixing this (`test_criterion_1_passes_with_real_disjoint_split_artifacts`, `test_criterion_1_fails_with_real_overlapping_split_artifacts`) covering the PASS and FAIL paths with synthetic real-looking data, which weren't covered before (only the PARTIAL/no-data path was).
  - Verified: `python -m pytest tests/ test_ablation.py -v` → 18 passed, 2 skipped locally (no GPU data here); 20 passed on the real GPU box (`test_ablation.py`'s 2 tests ran for real there, since real data exists -- confirms the actual training path works end-to-end, not just the test harness).

## 2026-08-13 — Proactive resilience hardening (requested after two real crashes)

Motivated directly by the two crashes already hit this session (masked pytest failure, then a genuine e3c_compliance bug) -- these are no longer speculative failure modes, they're observed ones on this exact remote environment (shared GPU, SSH-dependent access, multi-hour unattended runs). Three independent layers added, each covering a different failure scope. **None of this changes any reported number** -- it's exclusively about surviving interruptions without losing progress or silently corrupting results.

- **`src/train_pca.py`: real epoch-level checkpoint/resume.** Previously, an interrupted run could only be restarted from epoch 1 (the per-seed skip-if-`test_metrics.json`-exists logic in `run_gpu_pipeline.sh` was the only resumability, and it was all-or-nothing per seed). Now: `resume_checkpoint.pth` (model/optimizer/scheduler state, epoch, best-so-far tracking, full history) is saved after every epoch, written via temp-file + atomic `os.replace` so a crash mid-save can never leave a corrupt file at the real path. On startup, if that checkpoint exists, training resumes from `epoch+1` instead of 1; if loading it raises any exception (corruption, version mismatch), that's caught, logged, and the seed falls back to a fresh start rather than crashing again. Deleted automatically once the seed completes (`test_metrics.json` written), so a finished seed's directory never looks "still interrupted."
  - Honesty note (also in the code): a resumed run is not promised to be bit-identical to an uninterrupted run of the same seed -- the RNG trajectory across the interruption differs. It's still a real, honestly-trained result; just not claimed to be more reproducible than it actually is.
  - Verified for real (not just read): `tests/test_train_pca_resume.py`, 4 tests, real CPU training on tiny synthetic data (not mocked) -- confirms resume continues from the correct epoch without restarting or duplicating history, a corrupted checkpoint falls back gracefully instead of crashing, and the "checkpoint already at the epoch cap" edge case (interrupted between the training loop finishing and final save) skips straight to evaluation without a `NameError` on the loop variable.
  - Found and fixed one real bug in my own first draft of the test while writing it: the injected "resumed" checkpoint didn't also seed `best_model.pth` in the output directory (a real interrupted run always has one, saved whenever an epoch improved) -- the test itself doesn't lie about that, `best_model.pth` is legitimately required at final-eval time.

- **`run_gpu_pipeline.sh`: one seed's failure no longer kills the other 39.** Previously, `run_arm()`'s per-seed training call had no error handling at all -- any single seed crashing (`set -e` was global) aborted the entire remaining sweep, discarding whatever the other seeds/arms had already completed or were mid-way through. Now: each seed's `train_pca.py` invocation is wrapped in `if ! cmd; then ...; continue; fi` (a command's failure inside an `if` condition doesn't trigger `set -e`, by design -- this is what lets one seed fail without the rule breaking everywhere else), failures are collected into a `FAILED_RUNS` array and reported in a clear summary at the end (not hidden), and each seed's log is now appended to (`tee -a`) rather than overwritten, so a later retry of a previously-failed seed doesn't erase what happened last time.

- **`run_gpu_pipeline_supervisor.sh` (new file): bounded-retry wrapper for the orchestrator itself.** Covers the one failure scope the two layers above don't: the top-level `run_gpu_pipeline.sh` process dying outright (not an individual seed) -- e.g. the OOM killer hitting the parent process, a transient preflight failure. Retries up to 5 times with a 60s backoff between attempts; each retry is cheap because of the two resume layers above (re-running from scratch only re-does the fast setup steps, not all 40 training runs). Deliberately bounded, not infinite -- gives up loudly after 5 attempts rather than silently looping on a real, persistent bug forever (retrying forever would just burn GPU-hours while hiding the problem, which is exactly the failure mode this whole audit exists to catch elsewhere).

- **`pipeline_status.sh`: two more improvements.** (1) Now distinguishes "seed never started" from "seed has a resume checkpoint but isn't done yet" (in-progress or previously-failed-but-retryable) in the Phase 2 completion count, instead of lumping both into "not complete." (2) Tightened the `pgrep` pattern that false-positived on an unrelated process from a different project earlier this session (now requires `bash`/`sh` immediately before the script name) -- noted in-comment that this still can't be made fully airtight without also checking `cwd`/`ppid`, and suggested a manual `ps -p <pid> -f` cross-check when in doubt.

- **`PHASE5_SCOPE_PLAN.md`:** Quick Start now launches via the supervisor (recommended for the real run) instead of `run_gpu_pipeline.sh` directly, with a new "Resilience" section summarizing all three layers above.
