**Status of this document:** Phase 2 (deep audit) deliverable. Per audit ground rules, this file is never deleted — only the Status column is updated as findings are fixed, confirmed benign, or superseded. Do not delete rows.
**Methodology:** Six parallel full-file-read audits (data/leakage, model/architecture, training/seeds, evaluation/statistics, ablations+governance-scripts, figures/tables), each instructed to read every assigned file completely and cite exact file:line. All findings marked `[VERIFIED BY ORCHESTRATOR]` were independently re-checked by directly reading the source, rendering the actual PDF, or querying an external source — not taken on the sub-agent's word alone, per the audit's own rule on high-stakes findings.

Severity definitions: **CRITICAL** = directly undermines a headline claim or shows a mechanism that can misrepresent results (whether or not currently exploited in the live manuscript). **HIGH** = a real correctness/fairness/traceability defect in something that currently feeds, or could easily feed, a reported number. **MEDIUM** = dead code, duplication, or fragility that is a standing risk but not currently miscalculating anything confirmed. **LOW** = cosmetic, uncertain, or low-impact.

Status values used below: `OPEN` (found, not yet actioned), `NEEDS-DECISION` (requires your sign-off on whether it's a bug fix or a methodological change per rule 7).

## Zero-automated-coverage note (cross-cutting)

The repository's single most safety-critical guarantee — the inter-patient DS1/DS2 split with no patient overlap between train and test — has **zero automated regression coverage** anywhere in the repo. `split.py`'s own disjointness assertions only run if the file is executed directly as `__main__`; neither `smoke_test.py` nor `test_ablation.py` (the only two test-like files in the repo) touches the data, training, or evaluation clusters at all. This is the direct target of the domain-specific integrity rule agreed for this audit ("no metric/model/seed selection may ever touch test-set labels") — the split mechanism itself is correctly implemented everywhere it was checked (see Positive Findings below), but it currently has no regression test, so a future refactor could break it silently. **Recommend a regression test for Phase 4 regardless of whether any other finding here requires one.**

**FIXED 2026-08-12** — see CHANGELOG.md. `tests/test_split_integrity.py` now covers: `split.py`'s own three-way disjointness and DS1 partition, the 201/202 same-patient split, and (per H16) that the *alternate* `VAL_RECORDS` lists in `process_data.py`/`process_extended_rr.py`/`process_sequence.py` never overlap `TEST_RECORDS` either — while explicitly documenting (not silently "fixing") that those alternate lists still diverge from `split.py`'s own list, since reconciling them is the open H16 methodological question, not a bug this test should paper over.
